Best practices for scientific programming

Keywords

scientific programming, file organization, data management, analysis pipeline, unit testing

Learning objectives

By the end of this workshop, participants will be able to:

  1. Design a consistent file and folder structure for a scientific study, including naming conventions that support automated analysis and long-term reuse of data.
  2. Structure a data analysis pipeline as a series of separate, clearly named scripts — each performing a distinct step — moving from raw data through summary statistics and figure creation.
  3. Write readable, reusable code using functions and meaningful variable names, and apply unit testing to verify that code produces correct results.

Workshop

Presented by: Dr. James Finley

Overview

Why Programming Practices Matter in Science

Dr. Finley opens by framing the importance of good programming practices using a “house of cards” analogy: scientific work can be elegant but fragile when built on weak foundations. He describes two recurring failure modes from his own career. First, as a graduate student, he submitted a paper, received reviewer feedback months later requesting reanalysis, and found his files too disorganized to work with efficiently. Second, as a faculty member, he has experienced situations where a student defended or left the lab and the remaining data and code were difficult for anyone else to use. These experiences directly motivated the practices described in this workshop.

Phases of a Programming Workflow

Finley distinguishes two broad phases in scientific programming. The first is a prototyping phase, in which the goal is to explore data and get things working quickly — adding test cases and analyses to a single script, reusing existing code, and accepting something that works for the moment. The second is a development phase, in which code is refined to be robust, well-documented, and shareable. He notes that researchers often remain in the prototyping phase indefinitely, and that a key discipline of the workshop is knowing when and how to transition to higher-quality code. He also briefly mentions a third phase — sharing work publicly — noting that data funded by public money should ultimately be made available to the community, but that this requires adequate documentation and archiving.

Documenting Your Experimental Protocol

Before data collection begins, Finley recommends writing a detailed experimental protocol in a Word document or Google Doc. The protocol should list every step of the experiment, including verbatim instructions given to participants, consent procedures, and screenshots of relevant software settings. Finley states he has never seen an experimental protocol that is too detailed. The goal is that a new lab member, already familiar with basic equipment, should be able to follow the protocol step by step without additional guidance. He also recommends having another student attempt to execute a new protocol as a way to identify steps that are not well defined.

File Organization and Naming Conventions

Finley recommends defining a folder structure for each study before data collection begins. A typical structure might include separate folders for individual subjects, group data, analysis scripts, and papers or presentations. Once the structure is defined, it should be applied consistently across all participants. File names should be machine-readable: no spaces, consistent capitalization, and a consistent number of digits for numerical IDs. On the last point, he explains that without leading zeros, a file system will sort “subject11” before “subject2” because it compares character by character. For date stamps, he recommends year-month-day format with 24-hour time. He also emphasizes that participant names or initials must never appear in file names, as this would make the data identifiable and would no longer be HIPAA compliant.

Metadata, README Files, and Off-Boarding

Supporting documentation — referred to as metadata — should accompany all data. Finley recommends plain-text README files that describe variable coding, units, omitted items in clinical assessments, and other details that cannot easily be embedded in standard data files. He notes that well-maintained metadata allow a researcher to return to data collected years earlier and get up to speed quickly. He also describes an off-boarding checklist he instituted in his lab, which requires graduating students to organize all physical documents (consent forms, data collection sheets), digital data, experiment code, and analysis scripts, and to review them with Finley before he signs off on their dissertation defense. He describes this as a requirement for graduation in his group.

Knowing Your Data

Before writing analysis code, Finley recommends developing a clear understanding of four aspects of your data: how the data were collected (protocol, hardware, and any factors that might influence data properties); the sampling frequency, especially for time-series data such as force, EMG, or marker position; the units of each variable (confusion between meters and millimeters, or degrees and radians, is a common and consequential error); and the file format. On formats, he distinguishes interoperable formats — CSV, Excel, and JSON, which can be read across programming languages and statistical software — from proprietary formats such as MATLAB’s MAT files and motion-capture C3D files, which may not be readable outside their native software.

Building a Data Analysis Pipeline

Finley outlines a data analysis pipeline that moves from data import through quality control, preprocessing, computation of summary measures, figure creation, and statistical analysis. He recommends that the bulk of these steps be automated rather than executed manually. He illustrates this with a four-script MATLAB pipeline shared with workshop participants: the scripts are numbered to indicate run order and named with action verbs — simulate data, combine data, summarize data, and create figures. He also recommends analyzing the first participant’s complete dataset before collecting all participants’ data, because doing so frequently reveals weaknesses or gaps in the pipeline that can be corrected before large-scale data collection begins.

Writing Readable and Reusable Code

Finley offers several practical recommendations for code quality. He advises against single-letter variable names such as x, y, i, or j, recommending instead that names reflect what the variable represents — for example, naming a loop variable “participant” rather than “i” when cycling through participants. He recommends breaking complex operations across multiple lines rather than writing long single-line expressions. He also cautions strongly against copying and pasting code blocks and changing variable names: this practice increases the probability of introducing hard-to-detect errors, because the code will run and may produce a plausible result even when a name has been missed. The recommended alternative is to write functions. MATLAB includes a refactoring feature that converts selected lines of code into a local function by right-clicking and selecting “convert to a local function,” which Finley demonstrates in the workshop. A local function is appropriate when the operation is unlikely to be needed in other scripts; if the function may be reused across projects, it should be saved as a separate function file.

Verifying Code Correctness

Finley emphasizes that a lack of error messages does not guarantee correct results. He illustrates this with a code example in which the same variable is plotted on both axes of a figure: the script produces no errors and the result looks plausible (an upward trend), but the figure is wrong — once the correct variable is placed on the y-axis, the trend disappears. He recommends unit testing as a formal way to verify correctness: writing test code that supplies known inputs to a function and checks whether the output matches the expected value. MATLAB provides a tutorial course on unit testing that Finley recommends. He also briefly describes version control, explaining that the simplest approach is to save a working script under a new name before making changes, so that the prior version is preserved. He notes that GitHub is a more formal tool for version control and code sharing, though he does not cover it in depth in this workshop.

Q&A: MATLAB Compared to Other Languages

During the Q&A portion of the workshop, an attendee asked about using MATLAB versus other languages. Finley noted that the majority of the movement science and biomechanics community still uses MATLAB, while researchers in neuroimaging have largely moved to Python. He described MATLAB as easy to teach, with centralized and well-organized documentation resources. He also noted that data can be exported as CSV or plain-text files regardless of which language is used for analysis, making data sharing possible across communities even when code cannot be directly reused.
