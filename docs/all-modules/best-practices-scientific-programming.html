Best practices for scientific programming

Keywords

scientific programming, file organization, data management, analysis pipeline, unit testing

Learning objectives

By the end of this workshop, participants will be able to:

  1. Design a consistent file and folder structure for a scientific study, including naming conventions that support automated analysis and long-term reuse of data.
  2. Structure a data analysis pipeline as a series of separate, clearly named scripts — each performing a distinct step — moving from raw data through summary statistics and figure creation.
  3. Write readable, reusable code using functions and meaningful variable names, and apply unit testing to verify that code produces correct results.

Workshop

Presented by: Dr. James Finley

Overview

Why Programming Practices Matter in Science

Good programming practices matter because scientific work can be elegant but fragile when built on weak foundations — a “house of cards” that can collapse at a critical moment. Two recurring failure modes illustrate this risk. The first occurs when a researcher submits a paper, receives reviewer feedback months later requesting reanalysis, and finds their files too disorganized to work with efficiently. The second occurs when a student defends or leaves a lab and the remaining data and code are difficult for anyone else to use. The practices described in this workshop are directly motivated by these kinds of failures.

Phases of a Programming Workflow

Scientific programming involves two broad phases. The first is a prototyping phase, in which the goal is to explore data and get things working quickly — adding test cases and analyses to a single script, reusing existing code, and accepting something that works for the moment. The second is a development phase, in which code is refined to be robust, well-documented, and shareable. Researchers often remain in the prototyping phase indefinitely; a key discipline is knowing when and how to transition to higher-quality code. A third phase — sharing work publicly — is also important: data funded by public money should ultimately be made available to the community, but this requires adequate documentation and archiving.

Documenting Your Experimental Protocol

Before data collection begins, write a detailed experimental protocol in a Word document or Google Doc. The protocol should list every step of the experiment, including verbatim instructions given to participants, consent procedures, and screenshots of relevant software settings. A protocol can never be too detailed. The goal is that a new lab member, already familiar with basic equipment, should be able to follow the protocol step by step without additional guidance. Having another student attempt to execute a new protocol is a reliable way to identify steps that are not well defined.

File Organization and Naming Conventions

Define a folder structure for each study before data collection begins. A typical structure includes separate folders for individual subjects, group data, analysis scripts, and papers or presentations. Once the structure is defined, apply it consistently across all participants. File names should be machine-readable: no spaces, consistent capitalization, and a consistent number of digits for numerical IDs. Without leading zeros, a file system will sort “subject11” before “subject2” because it compares character by character. For date stamps, use year-month-day format with 24-hour time. Participant names or initials must never appear in file names: this would make the data identifiable and render it no longer HIPAA compliant.

Metadata, README Files, and Off-Boarding

Supporting documentation — referred to as metadata — should accompany all data. Plain-text README files should describe variable coding, units, omitted items in clinical assessments, and other details that cannot easily be embedded in standard data files. Well-maintained metadata allow a researcher to return to data collected years earlier and get up to speed quickly. An off-boarding checklist is a practical way to enforce these standards in a lab setting: graduating students organize all physical documents (consent forms, data collection sheets), digital data, experiment code, and analysis scripts, and review them with the principal investigator before dissertation defense sign-off. Treating this review as a requirement for graduation helps ensure that data and code remain usable after a student leaves.

Knowing Your Data

Before writing analysis code, develop a clear understanding of four aspects of your data: how the data were collected (protocol, hardware, and any factors that might influence data properties); the sampling frequency, especially for time-series data such as force, EMG, or marker position; the units of each variable (confusion between meters and millimeters, or degrees and radians, is a common and consequential error); and the file format. Interoperable formats — CSV, Excel, and JSON — can be read across programming languages and statistical software. Proprietary formats such as MATLAB’s MAT files and motion-capture C3D files may not be readable outside their native software.

Building a Data Analysis Pipeline

A well-designed data analysis pipeline moves from data import through quality control, preprocessing, computation of summary measures, figure creation, and statistical analysis. The bulk of these steps should be automated rather than executed manually. A four-script MATLAB pipeline illustrates this structure: scripts are numbered to indicate run order and named with action verbs — simulate data, combine data, summarize data, and create figures. Analyzing the first participant’s complete dataset before collecting all participants’ data is a valuable step, because it frequently reveals weaknesses or gaps in the pipeline that can be corrected before large-scale data collection begins.

The majority of the movement science and biomechanics community uses MATLAB, while researchers in neuroimaging have largely moved to Python. MATLAB is relatively easy to teach and has centralized, well-organized documentation. Regardless of which language is used for analysis, data can be exported as CSV or plain-text files, making data sharing possible across communities even when code cannot be directly reused.

Writing Readable and Reusable Code

Several practices improve code readability and reusability. Avoid single-letter variable names such as x, y, i, or j; instead, choose names that reflect what the variable represents — for example, naming a loop variable “participant” rather than “i” when cycling through participants. Break complex operations across multiple lines rather than writing long single-line expressions. Avoid copying and pasting code blocks and changing variable names: this practice increases the probability of introducing hard-to-detect errors, because the code will run and may produce a plausible result even when a name has been missed. The recommended alternative is to write functions. MATLAB includes a refactoring feature that converts selected lines of code into a local function by right-clicking and selecting “convert to a local function.” A local function is appropriate when the operation is unlikely to be needed in other scripts; if the function may be reused across projects, it should be saved as a separate function file.

Verifying Code Correctness

A lack of error messages does not guarantee correct results. A common illustration of this is a script that plots the same variable on both axes of a figure: the script produces no errors and the result looks plausible (an upward trend), but the figure is wrong — once the correct variable is placed on the y-axis, the trend disappears. Unit testing is a formal way to verify correctness: test code supplies known inputs to a function and checks whether the output matches the expected value. MATLAB provides a tutorial course on unit testing. For version control, the simplest approach is to save a working script under a new name before making changes, so that the prior version is preserved. GitHub is a more formal tool for version control and code sharing.
